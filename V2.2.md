# V2.2 — Placeholder-first cold-start hydration

## Purpose

Use this guide when Rebirth reaches the end of the financial refresh but then
disconnects, reloads, or remains on one of these messages:

```text
Publishing the validated snapshot atomically
Server refresh completed; synchronising this browser
Opening validated dashboard
```

This patch fixes two related post-publication problems:

1. Risk and Aggregate P&L are built eagerly inside the page layout and then
   rebuilt by their normal callbacks.
2. Revision 1 can be treated as browser-ready while the financial refresh is
   still running. For a coordinator-owned refresh, readiness can also be
   reported before its worker has returned from `refresh()`.

It does **not** fix a refresh that fails at a different Market Underlying on
each run. That earlier symptom is normally connector volume, concurrency, rate
limiting, thread safety, or an I/O timeout. See `FIX7.md` for the FX bulk-call
experiment and `V2.md` for the wider cold-start assessment.

This guide refines:

- `FIX10.md`, Step 1: true startup completion;
- `FIX10.md`, Step 8: deferred initial tables;
- `V1.md`: avoid the initial duplicate Risk-page render;
- `V2.md`: defer work that is not required for first paint.

## What must remain unchanged

Do not remove or weaken:

- connector validation;
- Open/Current quote uniqueness;
- `many_to_one` Risk-to-Market validation;
- Portfolio and Reported Underlying mapping;
- P&L formulas;
- atomic snapshot publication;
- last-good snapshot retention during warm refreshes;
- the process-wide refresh lock;
- `/healthz` or `/progressz`.

The target flow is:

```text
small shell
  -> background refresh
  -> atomic revision 1
  -> financial refresh reaches terminal progress
  -> the coordinator-owned worker returns, or external financial progress is terminal
  -> small Risk-page structure with stable IDs
  -> existing callbacks own the first visible table render
```

The target is **not** to move connector or financial calculations into a Dash
request.

running copy, import it from:

```python

```

### Behaviour

```text
browser revision 0, cache revision 1 -> no heavy render
browser revision 1, cache revision 1 -> render
browser revision 1, cache revision 2 -> wait for browser revision 2
browser revision 2, manager/cache revision 1 -> reject an inconsistent future token
```

Exact equality is deliberate. A `browser_revision < cache.revision` check is
not sufficient because it allows a future browser token to render an older
cache. Calling `cache.current()` first also closes the ordinary manager-ahead
case when the browser token is stale. A later revision Store update retriggers
that normal stale-browser request.

The application must not publish a browser token that is ahead of the manager.
If that invariant is violated, reject the request and log, reload, or retry the
handoff. Do not assume that the cache will later catch up: a Store already at
revision 2 may not change again and therefore may not retrigger the callback.

This keeps the component tree and its financial frame on the same committed
revision.

## 4. Make Risk dashboard preparation single-flight

Without this step, several callbacks can all notice revision 1, deep-copy the
dashboard, and prepare it concurrently.

### File

```text
rebirth/pages/risk/s02_state.py
```

`_RiskDataCache` already uses `RLock`. Keep it.

### 4.1 Replace `current()`

Replace the method with this simple revision-owned version:

```python
def current(self, manager: RefreshManagerProtocol | None) -> pd.DataFrame:
    if manager is None:
        with self._lock:
            return self._frame

    with self._lock:
        manager_revision = int(manager.health.revision)
        if self._revision == manager_revision:
            return self._frame

        dashboard = manager.read_frame("dashboard_frame")
        return self.replace_frame(dashboard.frame, dashboard.revision)
```

The `RLock` is deliberately held while the one new revision is read and
prepared. Other callbacks wait and then reuse the prepared frame. This is not
a general application lock and it does not cover connector work.

### 4.2 Replace `replace_frame()`

The revision check must happen before `prepare_risk_data()`:

```python
def replace_frame(self, frame: pd.DataFrame, revision: int) -> pd.DataFrame:
    """Prepare and publish one dashboard frame per committed revision."""
    selected_revision = int(revision)
    with self._lock:
        if selected_revision <= self._revision:
            return self._frame

        prepared = prepare_risk_data(frame)
        self._frame = prepared
        self._revision = selected_revision
        self._filtered.clear()
        self._rendered.clear()
        self._promotion_generations.clear()
        return prepared
```

Because the lock is an `RLock`, `current()` may safely call `replace_frame()`
while holding it.

### Why this is intentionally serial

Preparing one revision once is cheaper and safer than preparing the same large
DataFrame four times in parallel. Normal filtering and interaction callbacks
continue after the prepared frame is published.

Do not replace this with a module-global DataFrame shared outside the cache.

def materialize_initial_dashboard() -> html.Div:
    """Build one committed Risk page or retain a safe startup shell."""
    try:
        for _attempt in range(2):
            control = refresh_manager.control_snapshot
            prepared = cache.current(refresh_manager)
            if cache.revision == int(control.revision):
                break
        else:
            raise RuntimeError(
                "Could not read one consistent initial dashboard revision"

            prepared,
            control,
            refresh_enabled=True,
            stage_delays=refresh_manager.stage_delays,
            include_shared_refresh_shell=False,
        )
    except Exception as error:

        app.logger.error(
            "Cube startup UI preparation failed; incident=%s type=%s",
            incident_id,

            f"Dashboard preparation failed (incident {incident_id}). "
            "No dashboard was published; retry after checking the server log."

        return build_initial_load_layout(
            stage_delays=refresh_manager.stage_delays,
            error=safe_error,
            include_shared_refresh_shell=False,
        )

    app.server.config[STARTUP_UI_ERROR_CONFIG_KEY] = None

## 7. Prevent concurrent full-page hydration

The frame cache prevents duplicate DataFrame preparation. This small lock also
prevents two interval callbacks from constructing the full page at the same
time.

### File

```text
rebirth/pages/risk/s15_refresh.py
```

Add:

```python
from threading import Lock
```

Inside `register_refresh_callbacks()`, before the callback definitions, add:

```python
startup_hydration_lock = Lock()
```

In `load_initial_snapshot_after_first_paint()`, replace the successful branch
with:

```python
if startup.phase == "succeeded" and refresh_manager.health.revision > 0:
    if not startup_hydration_lock.acquire(blocking=False):
        raise PreventUpdate
    try:
        return materialize_initial_dashboard()
    finally:
        startup_hydration_lock.release()
```

A second browser or interval tick waits for a later poll rather than consuming
another Gunicorn thread with the same large construction.

The lock does not cache the Dash component tree. Do not retain a full component
tree globally; that would trade transient work for permanently retained
memory.

This is an overlap guard, not an exactly-once guarantee for the lifetime of the
page. The lock is released when Python finishes constructing the return value,
before Dash has necessarily serialized and applied that response in the
browser. A later tick can therefore construct the layout again after the lock
is released while the placeholder is still mounted. That bounded sequential
race is preferable to retaining a process-global component tree or a permanent
"completed" flag, either of which can strand a second browser or a browser that
lost the first response.

### Optional polling reduction

In `rebirth/ui/s04_components.py::build_initial_load_layout()`, change only:

```python
interval=500,
```

to:

```python
interval=1_000,
```

The interval performs lightweight status polling. The completion gate and
locks are the real fix; the slower interval merely reduces duplicate traffic.

## 8. Do not publish browser readiness while the financial refresh is running

Revision 1 means that a valid snapshot exists. During cold startup it does not
yet prove that financial progress is terminal. For a coordinator-owned refresh,
the return of its `_run()` worker is the strongest completion signal. For an
external writer, `progress.running=False` only proves that the financial stages
are terminal; the external thread may still be finishing metrics or logging.

### File

```text
rebirth/app/s04_startup.py
```

### 8.1 Add one safe inference helper

Add this next to `_revision()`:

```python
def _published_and_stopped(self) -> bool:
    """Return whether a revision exists and financial progress is terminal."""
    if self._revision() <= 0:
        return False
    try:
        return not bool(self._manager.progress.running)
    except Exception:
        # Missing progress is not proof of completion.
        return False
```

Despite its short name, this helper does not prove that an external Python
thread has completely returned. It is for **inferred financial completion**.
The coordinator's own `_run()` remains authoritative after its direct
`refresh()` call returns.

### 8.2 Correct `start()`

The current method checks revision before checking its own worker. Reverse that
ordering. Inside its locked section, use this opening:

```python
worker_alive = self._worker is not None and self._worker.is_alive()
if worker_alive or self._phase in {"running", "stalled", "succeeded"}:
    return False

if self._revision() > 0:
    if self._published_and_stopped():
        self._phase = "succeeded"
        self._error = None
    return False
```

Then keep the existing failed/retry, timer, attempt, and worker-launch logic.
Remove the later duplicate worker/phase test.

This prevents an owned worker that has just published revision 1 from being
reported complete while it is still returning from `refresh()`.

### 8.3 Correct `schedule_start()`

Inside its locked section, calculate liveness before the revision shortcut:

```python
worker_alive = self._worker is not None and self._worker.is_alive()
timer_alive = self._start_timer is not None and self._start_timer.is_alive()
if worker_alive or timer_alive or self._phase != "idle":
    return False

    if self._published_and_stopped():
        self._phase = "succeeded"
        self._error = None
    return False
```

Then keep the existing Timer construction. Remove the old duplicated revision,
worker, timer, and phase checks.

### 8.4 Correct `status()`

Replace the unconditional revision-success block with:

```python
worker_alive = self._worker is not None and self._worker.is_alive()
if (
    self._phase != "succeeded"
    and not worker_alive
    and self._published_and_stopped()
):
    self._phase = "succeeded"
    self._error = None
```

Do not demote a coordinator that already completed revision 1 merely because a
later warm refresh is running. This preserves the visible last-good snapshot.

Keep the watchdog logic after it. The watchdog reports a stalled call; it does
not cancel the writer.

`_run()` remains the normal owner of success after `refresh()` returns. Keep:

```python
copy_result=False
```

### 8.5 Correct the opening of `_run()`

A scheduled worker can begin just after another writer publishes. Replace the
opening revision shortcut in `_run()` with:

```python
if self._revision() > 0:
    if self._published_and_stopped():
        self._succeed(attempt)
    else:
        self._follow_existing_writer(attempt)
    return
```

Do not use revision alone as proof that the external financial work is
terminal.

### 8.6 Correct `_follow_existing_writer()`

Read progress before accepting the revision:

```python
def _follow_existing_writer(self, attempt: int) -> None:
    while True:
        try:
            progress = self._manager.progress
            running = bool(progress.running)
            progress_error = progress.error
        except Exception as error:
            self._fail(attempt, error)
            return

        if self._revision() > 0 and not running:
            self._succeed(attempt)
            return
        if not running:
            self._fail(
                attempt,
                RuntimeError(
                    str(progress_error)
                    if progress_error
                    else "The existing refresh ended without publishing revision 1."
                ),
            )
            return
        sleep(0.2)
```

This does not delay an already-successful coordinator during later warm
refreshes. The existing last-good revision remains usable.

### 8.7 Correct `_run()` exception handling

The stale and generic exception paths must use the same completion rule. If a
revision exists but financial progress is still running, follow that writer
instead of marking startup successful.

Replace those two branches with:

```python
except StaleRefreshError:
    if self._published_and_stopped():
        self._succeed(attempt)
    elif self._revision() > 0:
        self._follow_existing_writer(attempt)
    else:
        self._fail(
            attempt,
            RuntimeError(
                "The initial refresh became stale before revision 1 was published."
            ),
        )
except Exception as error:
    if self._published_and_stopped():
        self._succeed(attempt)
    elif self._revision() > 0:
        self._follow_existing_writer(attempt)
    else:
        self._fail(attempt, error)
```

Do not keep an older branch that calls `_succeed()` merely because
`self._revision() > 0`. That recreates the early-hydration race through an
exception path.

### Endpoint interpretation

| Observation | Meaning |
|---|---|
| `/healthz` and `/progressz` both disappear and revision resets to 0 | process restart or memory kill |
| endpoints pause and return with the same revision | CPU or request-thread starvation |
| endpoints remain healthy while the page reconnects | callback, proxy, serialization, or browser failure |
| revision 1 and `running=true` | a snapshot was published but the financial refresh is not terminal |
| revision 1 and `running=false` | financial refresh is complete; remaining work is UI hydration |

## 13. Rollback boundaries

Keep each section as its own commit if possible:

```text
v2.2/placeholder-layout
v2.2/revision-guard
v2.2/single-flight-cache
v2.2/placeholder-route
v2.2/completion-barrier
```

Each change can be rolled back without changing stored data or financial
schemas.

If a placeholder remains forever, check these first:

1. the rendering callbacks were not changed to `prevent_initial_call=True`;
2. `data-revision-store` reaches the same revision as `cache.revision`;
3. `progress.running` eventually becomes false;
4. `startup_phase` becomes `succeeded`;
5. all callback output IDs still exist in the layout.

Do not solve a permanent placeholder by deleting revision checks or forcing
missing data to zero.

## Final success criteria

V2.2 is successful only when:

1. revision 1 is published atomically;
2. no heavy browser hydration begins before cold completion;
3. layout construction builds neither initial table;
4. revision 0 builds neither initial table;
5. one explicit committed-revision callback invocation builds the requested
   visible table, with no concurrent duplicate full-layout build;
6. concurrent callbacks prepare one dashboard per revision;
7. Base Activity 1, 2 and 3 remain selected;
8. Risk, dRisk and P&L totals are unchanged;
9. warm refreshes retain the last good revision;
10. `/healthz` and `/progressz` remain reachable during synchronisation.

If these pass but failures still occur at random Market Underlyings, V2.2 has
done its job; continue with connector batching and rate-limit work rather than
adding more browser-side defenses.
