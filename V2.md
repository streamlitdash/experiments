# v2 — Cold-start defensive-code experiment

## Objective

Reduce Rebirth V4.1 cold-start time and peak memory without weakening financial
validation, atomic publication, or last-good-snapshot behaviour.

This assessment is based on Rebirth `main` at `cdf1e77` and the relevant
`cold-start-change` branch at `7d60446`.

## Production-size estimate

Assuming the Underlying counts are totals across the named product families:

| Area | Approximate maximum position rows |
|---|---:|
| Credit | `350 × 10 tenors × 80 books = 280,000` |
| IR | `250 × 50 tenors × 200 portfolios = 2,500,000` |
| FX | `70 × 300 + 30 × 10 tenors × 300 = 111,000` |
| **Total** | **about 2,891,000 rows** |

This is before Gamma-derived, Cross Gamma, New Trades, Cashflow, or unmapped
rows. At this grain, one unnecessary full-frame copy can consume hundreds of
megabytes or more, and several overlapping copies can exceed a JupyterHub
memory limit.

## Main finding

The locks, revision checks, watchdog and transaction-level `try/except` blocks
are not causing the lag. Their healthy-path cost is very small.

The expensive defensive behaviour is:

1. copying every committed financial frame when only control metadata or the
   dashboard is needed;
2. retaining more than one prepared dashboard;
3. copying and validating the same position-grain data repeatedly;
4. retrying almost every Market exception four times under a 20-thread fan-out;
5. building Search and the first large tables before the initial dashboard is
   usable.

## Experiment 1 — Remove broad snapshots from hydration

Current hot spots:

- `rebirth/services/s02_state.py::_copy_snapshot()` deep-copies six frames;
- `rebirth/pages/risk/s15_refresh.py::load_initial_snapshot_after_first_paint()`
  requests the broad snapshot;
- `hydrate_shared_refresh_shell()` requests another broad snapshot even though
  the shell needs only control metadata;
- `rebirth/app/s07_factory.py::risk_snapshot_cache` retains another complete
  copied snapshot.

Change the cold handoff to use:

- one `control_snapshot` for dates, readiness and settings;
- one revision-consistent `read_frame("dashboard_frame")` for Risk data;
- no retained `risk_snapshot_cache`.

The shared shell should use `control_snapshot` only. Add `refresh_reason` to the
compact control model if the “Last automatic run” text must be preserved.

This is the safest and highest-value deletion.

## Experiment 2 — Keep one prepared dashboard

The factory and `rebirth/pages/risk/s02_state.py::_RiskDataCache` currently own
separate prepared dashboards. Cold Risk can prepare one, then later navigation
to Risk or P&L can prepare and retain a second copy.

Use one revision-aware prepared-dashboard cache for Risk and P&L.

Also move the revision check in `_RiskDataCache.replace_frame()` before
`prepare_risk_data()`, then recheck before publication. A duplicate or stale
revision must return the existing frame without preparing millions of rows and
discarding the result.

## Experiment 3 — Use one owned validation copy

`rebirth/domain/s03_calculations.py::get_product_risk()` currently moves through
approximately five or six complete copies: source loading, product enforcement,
nonblank validation, numeric validation, optional Credit validation, and final
projection.

Keep one copy at the connector ownership boundary, then validate and normalize
that owned frame without copying it again at every helper.

Two particularly simple candidates are the copies of `validated_risk` and
`validated_market` in `get_product_pl()`. They are copied immediately before
`pandas.merge()` creates a new result. Remove those two copies after adding a
test proving that both supplied frames remain unchanged.

The release path has similar redundant copies in:

- `_merge_validated_config()`;
- mapped/unmapped slicing in `_release_pl_views()`;
- `to_dashboard_frame()`;
- the dashboard projection used to create `SearchCatalog`.

Do not remove the actual numeric, key, tenor, mapping, threshold or merge
cardinality checks. Remove repeated ownership copies around those checks.

## Experiment 4 — Avoid UI revalidation of committed data

`rebirth/ui/s02_aggregation.py::prepare_risk_data()` copies the complete
dashboard and repeats checks already performed before atomic commit.

Its `_resolved_tenor_orders()` implementation is particularly expensive at IR
scale: it groups by Underlying and repeatedly scans each group for every tenor
label, for both tenor axes.

Keep `prepare_risk_data()` as the defensive public path for arbitrary or static
DataFrames. Add a trusted manager-owned path that:

- assumes the committed contract has already been validated;
- performs only the UI transformations that are still required;
- resolves missing tenor ranks on quote-grain unique keys and maps them once to
  positions, instead of repeatedly scanning Portfolio-grain rows.

## Experiment 5 — Replace blanket Market retries

`rebirth/services/s06_refresh.py` currently uses:

```python
_MARKET_MAX_WORKERS = 20
_MARKET_RETRIES = 4
_MARKET_RETRY_DELAY_SECONDS = 0.5
```

At approximately 700 Underlyings, Open plus Current produces about 1,400 first
attempts if the counts are totals across source types. The blanket policy can
turn that into about 7,000 attempts, and more if Underlyings repeat across
product specifications.

The current code retries almost every exception, including permanent
authentication, permission, programming and memory failures. It can create a
synchronised retry wave against the real service, while a permanently hung
call never reaches the retry code.

Replace the manager-wide catch-all policy with connector-owned behaviour:

- the concurrency actually allowed by that service and client session;
- batching where the connector supports it;
- a real per-call I/O timeout;
- at most explicitly transient retries;
- exponential backoff with jitter and a total deadline.

This thread pool runs inside the application in JupyterHub. Gunicorn is not
required for it to overload a connector.

## Defer work that is not required for first paint

These are not defensive checks, but they remain important cold-start costs:

- `SearchCatalog` is constructed before revision 1 is published;
- `build_layout()` immediately filters the complete dashboard;
- the initial Risk table and Aggregate P&L table are built eagerly;
- default Activity selection is calculated twice;
- dropdown options repeatedly scan full position-grain columns.

Build Search on first use and let existing callbacks render the large initial
tables after the basic committed page is visible.

## Do not remove

Keep:

- the process-wide refresh lock and StartupCoordinator deduplication;
- state and progress locks;
- `expected_revision` and reset-generation checks;
- `one_to_one` and `many_to_one` merge validation;
- connector-owned tenor authority and uniqueness checks;
- atomic commit and last-good-revision retention;
- transaction and UI publication exception barriers;
- the watchdog and lightweight health/progress endpoints.

Removing these gives almost no normal-path speed benefit and can instead launch
duplicate connector storms, publish mixed revisions, or silently multiply P&L.

## How to identify the failing phase

- **Process dies before revision 1:** focus on Market concurrency/retries,
  product P&L merges, release intermediates and eager Search construction.
- **Process dies immediately after revision 1:** focus on broad snapshot copies,
  duplicate preparation, tenor resolution and eager initial tables.
- **Python process remains alive but browser disconnects:** measure CPU time in
  preparation/layout and verify that the JupyterHub proxy can still reach
  `/healthz` and `/progressz`.

## Measurement gate

For every experiment, record the same real-data run:

```text
cold-start elapsed seconds
peak process RSS
revision reached
Risk rows
combined_pl rows
dashboard rows
Market rows
Market connector attempt count
release seconds
search seconds
dashboard preparation seconds
initial layout seconds
```

The checked-in benchmark currently prepares only 100,000 rows. Add a separate
production-shape experiment near 2.9 million rows and measure peak RSS, not only
elapsed time.

On the checked-in 10,572-row fixture, the measured DataFrame buffers were
approximately:

- broad snapshot: 15.0 MiB;
- dashboard: 6.78 MiB;
- prepared dashboard: 7.25 MiB.

A simple linear buffer estimate at 2.891 million rows is around 4 GiB for a
broad snapshot. Even one targeted dashboard read plus one prepared frame could
approach 3.75 GiB. These are planning estimates, not measured production RSS,
but they show why eliminating only the broad snapshot is necessary and still
may not be sufficient for a small JupyterHub container.

## Branch note

`cold-start-change` already implements targeted control/dashboard reads and
several release-copy reductions. It is directionally correct, but it is behind
`main` and does not solve duplicate prepared caches, manual-refresh broad
copies, resident Search state, or the full dashboard-read-plus-preparation
peak. Rebase or cherry-pick the relevant changes; do not deploy the stale
branch wholesale.

Apply the experiments independently and keep only changes that reduce measured
RSS/time while preserving the exact financial totals, row grain and failure
behaviour.
