# V1 — Cold-Startup Hydration Audit

## Summary

The startup coordinator itself is not the main source of lag. Its locks, status checks, single-writer guard and atomic publication are small and should remain.

The expensive behaviour happens around the coordinator: the same large Risk frame is repeatedly copied, validated, indexed and rendered after it has already passed the connector and release validations.

For Credit data with approximately 70 portfolios, 370 underlyings and 10 tenors, the application may process around 259,000 position rows. Several complete passes over that frame can therefore create substantial CPU work and temporary memory pressure.

This audit covers the `cold-start-change` branch of Rebirth V4.1 at commit `7d60446`. It is a static code-path assessment rather than a measured benchmark.

## Safest defensive work to remove

### 1. Stop copying the frame when no promotion change is needed

File: `rebirth/pages/risk/s11_promotion.py`

`apply_promotion_generation()` copies the entire filtered Risk frame when:

- there is no promotion generation;
- the baseline generation is active; or
- the requested generation is stale.

The frame supplied to this function is already privately owned by the filtering stage, and the following rendering stage does not mutate it.

The simple change is to return `frame` directly in those three branches. Keep the real merge/copy operation for a manually recalculated promotion generation.

### 2. Remove Risk and Market copies immediately before the P&L merge

File: `rebirth/domain/s03_calculations.py`

The P&L path copies the validated Risk and Market inputs immediately before calling `merge()`. Pandas creates a new merged frame, so those two input copies provide no useful isolation.

Remove the two pre-merge copies. Keep the merge validation and financial calculations.

### 3. Remove obsolete broad-snapshot compatibility fallbacks

Files:

- `rebirth/app/s07_factory.py`
- `rebirth/app/s02_contracts.py`

The factory catches missing `control_snapshot()` or `read_frame()` methods and falls back to obtaining and copying a broad snapshot. The manager protocol already requires both methods.

The fallback can therefore be deleted. This simplifies the code and prevents an accidental full-snapshot copy. It will not noticeably improve normal startup unless the fallback is currently being used.

### 4. Avoid repeating default-filter resolution

Files:

- `rebirth/pages/risk/s03_defaults.py`
- `rebirth/pages/risk/s16_view.py`

The initial layout resolves the default Risk filters more than once, and the resolver materialises the complete Activity column as a Python list.

Resolve the defaults once, reuse the result and operate on unique Activity values. This is a small but safe cleanup.

### 5. Reuse the requested-underlying result

File: `rebirth/services/s06_refresh.py`

Startup rescans and deduplicates the complete Risk frame more than once to obtain requested market underlyings.

Calculate this once after Risk has loaded and reuse it for the subsequent market requests.

## Larger defensive duplication to simplify carefully

### 6. Add a trusted-manager path through `prepare_risk_data()`

File: `rebirth/ui/s02_aggregation.py`

`prepare_risk_data()` currently:

- copies the complete dashboard frame;
- repeats numeric conversion and validation;
- repeats missing and non-finite checks;
- repeats breakdown checks; and
- revalidates tenor-order mappings over position-level rows.

The manager-generated dashboard frame has already passed connector, product, market and release validation. Repeating these checks at UI hydration is defensive duplication.

For frames read directly from `RefreshManager`, use a trusted path that performs only the transformations required for display. Retain the existing full validation path for frames supplied by external callers and tests.

Do not simply remove every check from the public function. The source of the frame must determine whether the trusted path is permitted.

### 7. Reduce repeated release validation

File: `rebirth/domain/s07_governance.py`

The release validator scans the completed dashboard frame again for values that were already guaranteed by upstream construction, including several numeric, string, status and order checks.

Keep a final release gate, but limit it to cross-field invariants that are not already proven by connector and product validation. Full strict validation can remain available for tests or a diagnostic mode.

### 8. Give SearchCatalog a trusted construction path

File: `rebirth/domain/s10_search.py`

Search catalogue construction copies and revalidates trusted dashboard and market data. Some combined-underlying validation is also repeated multiple times.

The application manager should use a trusted constructor. Retain the defensive constructor for direct library callers if that API is still required.

### 9. Use one prepared-dashboard cache

Files:

- `rebirth/app/s07_factory.py`
- `rebirth/pages/risk/s15_refresh.py`
- `rebirth/pages/risk/s17_callbacks.py`

The factory and Risk page maintain separate caches for prepared dashboard data. Both can prepare and retain a large frame for the same financial revision.

Use one cache as the authority for the prepared revision. This reduces duplicate preparation and memory retention without changing financial behaviour.

## Important cold-start work that is not defensive validation

These items are probably at least as important as the removable checks.

### Build market quote indexes lazily

File: `rebirth/ui/s02_aggregation.py`

`HierarchyAggregationIndex` eagerly builds Open, Current and Move indexes across the full position frame. The shallow initial Risk rows commonly request Risk only and do not use these market indexes.

Create each market index on its first `include_market=True` request. Preserve the existing quote hierarchy because it prevents a market quote from being weighted by the number of portfolios.

### Render the initial Risk page once

Files:

- `rebirth/pages/risk/s15_refresh.py`
- `rebirth/pages/risk/s16_view.py`
- `rebirth/pages/risk/s07_explorer.py`
- `rebirth/pages/risk/s14_workspacecallbacks.py`
- `assets/s12_refresh.js`

The page can currently be rendered in the server layout, again by callbacks using revision `0`, and again when the browser receives financial revision `1`.

Choose one initial rendering path and prevent revision-zero callbacks from rebuilding the same tables. Otherwise several expensive requests can occupy all server workers and make health or progress requests appear disconnected.

### Avoid repeated scans for promoted underlyings

The initial view opens every Risk Greek. With hundreds of promoted underlyings, tree construction can repeatedly filter the entire frame for individual promotion buckets.

If this remains expensive after the simpler changes, build a reusable grouped index for the promotion buckets. Do not change the initial open/closed behaviour unless the product requirement changes.

## Protections that should remain

Do not delete:

- atomic snapshot publication;
- the last-good snapshot fallback;
- the single startup writer and idempotence guard;
- revision consistency and stale-generation checks;
- connector schema and numeric validation at ingestion;
- position uniqueness and merge-cardinality validation;
- Open and Current market quote uniqueness;
- raw-underlying and reported-underlying authority;
- missing-market availability handling; or
- the quote aggregation rules that prevent portfolio-count weighting.

These protect financial correctness and are not the expensive part of cold-start hydration.

## Recommended implementation order

Start with the smallest changes:

1. Remove the no-op promotion copies.
2. Remove the pre-merge P&L copies.
3. Resolve defaults and requested underlyings once.
4. Build Open, Current and Move indexes lazily.
5. Prevent the duplicate revision-zero render.
6. Add the trusted-manager preparation path.
7. Consolidate the prepared-dashboard caches.
8. Finally, streamline the release and SearchCatalog validators if timing evidence still shows them as expensive.

Add timings around dashboard preparation, Risk table construction and Aggregate P&L construction before and after these changes. Existing refresh-stage timings finish before much of the hydration and browser-rendering work, so they do not currently show the complete cold-start cost.
