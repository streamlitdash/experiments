# v2.1 — Minimal hydration fix

## Goal

Test two changes after revision 1 commits:

1. copy only the dashboard data needed by Risk;
2. stop building the initial Risk and Aggregate P&L tables twice.

This is a proposed experiment for Rebirth V4.1 `main` at `cdf1e77`. At the
estimated production shape of about 2.891 million position rows, overlapping
full-frame copies can exceed a JupyterHub memory limit.

## What changes

Current:

```text
revision 1
  |-> Risk callback copies the complete six-frame snapshot
  |    -> build_layout builds both large tables
  |    -> the initial callbacks build both tables again
  |
  `-> shared-shell callback can copy the complete snapshot again
```

The two Dash callbacks are independent and can overlap.

Proposed:

```text
revision 1
  |-> Risk reads dashboard_frame only
  |    -> build_layout returns empty table targets
  |    -> existing callbacks build the tables
  |
  `-> shared shell reads control_snapshot only
```

## Fix 1 — Read only what hydration needs

### 1. Change cold Risk hydration

Edit `rebirth/pages/risk/s15_refresh.py`.

Import `ControlSnapshotProtocol` and `FrameReadProtocol` from
`rebirth.app.s02_contracts`.

Change `materialize_initial_dashboard()` to receive those two objects. Inside
its existing `try` block, replace `cache.replace(snapshot)` with:

```python
prepared = cache.replace_frame(dashboard.frame, dashboard.revision)
```

Pass `control`, not the broad snapshot, to `build_layout()`:

```python
layout = build_layout(
    prepared,
    control,
    refresh_enabled=True,
    stage_delays=refresh_manager.stage_delays,
    include_shared_refresh_shell=False,
)
```

Keep the existing incident logging and retryable loading shell.

In `load_initial_snapshot_after_first_paint()`, replace:

```python
return materialize_initial_dashboard(refresh_manager.snapshot)
```

with:

```python
control = refresh_manager.control_snapshot
dashboard = refresh_manager.read_frame("dashboard_frame")

if int(control.revision) != int(dashboard.revision):
    raise PreventUpdate

return materialize_initial_dashboard(control, dashboard)
```

The revision check prevents metadata from revision N being combined with data
from revision N+1. The existing 500 ms cold interval will try again, so do not
add another retry loop.

### 2. Change shared-shell hydration

In `hydrate_shared_refresh_shell()` in the same file, replace:

```python
refresh_manager.snapshot
```

with:

```python
refresh_manager.control_snapshot
```

The shell needs only revision, dates, status, settings, readiness and errors.

### 3. Update the type hints

Allow `ControlSnapshotProtocol | RefreshSnapshotProtocol` at these boundaries:

- `rebirth/pages/risk/s15_refresh.py::register_refresh_callbacks()`;
- `rebirth/pages/risk/s16_view.py::build_risk_date_editor()`;
- `rebirth/pages/risk/s16_view.py::build_layout()`;
- `rebirth/pages/risk/s17_callbacks.py::register_callbacks()`.

No new snapshot class is required.

### 4. Remove warm/reconnect broad reads

Also edit `rebirth/app/s07_factory.py`; otherwise warm construction or a Risk
page remount can call the broad snapshot again.

Use this exact pairing wherever the Risk page needs metadata plus its frame:

```python
control = refresh_manager.control_snapshot
dashboard = refresh_manager.read_frame("dashboard_frame")

if int(control.revision) != int(dashboard.revision):
    return build_initial_load_layout(
        stage_delays=stage_delays,
        include_shared_refresh_shell=False,
    )

prepared = prepared_committed_dashboard(
    revision=int(dashboard.revision),
    frame=dashboard.frame,
)
```

Pass that same `control` to `build_layout()`. Supplying the same frame and
revision to `prepared_committed_dashboard()` avoids a second independent read.

For a revision mismatch during warm app construction, use the ordinary cold
state:

```python
initial_snapshot = None
risk_data = pd.DataFrame()
```

This initializes the prepared cache to revision `-1` with no frame and lets the
normal page poll hydrate it.

Delete these factory variables:

```text
risk_snapshot_lock
risk_snapshot_revision
risk_snapshot_cache
```

Do not delete `RiskRefreshManager.snapshot` or `_copy_snapshot()` from
`rebirth/services/s02_state.py`. The experiment removes unnecessary UI callers;
it does not weaken the manager safety boundary.

## Fix 2 — Defer the two initial tables

Edit `rebirth/pages/risk/s16_view.py::build_layout()`.

Keep:

```python
initial_filter_values = default_risk_filter_values(risk_data)
```

Delete the block that creates:

```text
initial_filter_payload
default_filtered
initial_risk_frame
initial_open_rows
initial_risk_table

```

### 2. Return empty targets

Use:

```python

html.Div(id="aggregate-pl-grid")

html.Div(id="risk-grid", className="risk-grid")
```

Keep the surrounding panels and `dcc.Loading` components.

The Risk callback already calculates its default open rows when previous
context is empty. This becomes the one authoritative initial state instead of
briefly showing the eager state and then replacing it.


- `rebirth/pages/risk/s07_explorer.py::reduce_and_render_risk_view()`.

## Pass conditions

Keep the changes only if:

- cold Risk and shared-shell hydration never call `refresh_manager.snapshot`;
- the cold Risk callback reads one dashboard frame when its revision pair matches;
- no mixed control/dashboard revision is rendered;
- `build_layout()` returns empty Risk and Aggregate targets;
- both existing callbacks populate their targets;
- row counts and financial totals are unchanged;
- peak RSS or post-commit time improves;
- JupyterHub stays reachable through the first table render.

## Keep and rollback

Keep defensive `read_frame()` copying, locks, atomic commit, last-good state,
revision checks, connector validation, tenor authority and merge-cardinality
checks. They do not cause this duplicate hydration work.

Commit Fix 1 and Fix 2 separately. If either experiment fails its conditions,
revert only that commit.

Connector concurrency, SearchCatalog laziness, validation-copy cleanup and
prepared-cache consolidation remain separate experiments from `V2.md`.
